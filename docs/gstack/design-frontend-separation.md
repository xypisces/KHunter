## Problem Statement

KHunter 是一个 A 股量化交易系统，当前前后端耦合在同一个 Flask 应用中。前端是一个 2284 行的 `index.html` + 33 个 vanilla JS 文件（10 个顶层文件 + 23 个 modules/ 子目录），存在三个核心痛点：

1. **选股结果是黑盒**——系统输出股票列表但看不到选股过程，不知道为什么选中/淘汰
2. **K 线图不能交互**——原生 Canvas 手绘，不能缩放、不能切换周期、不能点击查看详情
3. **回测等待体验差**——长时间等待无反馈，结果只有数字没有可视化

## What Makes This Cool

**信号直接标在 K 线图上。** 选股命中点、回测买卖点全部叠加在可交互的 K 线图上——这是量化系统的核心体验升级。从"看表格猜逻辑"变成"看图理解策略"。

**实时进度推送。** 数据更新、选股、回测的进度通过 WebSocket 实时推送到前端，不再依赖轮询。用户能看到"正在处理第 127/3000 只股票"而不是转圈等待。

**lightweight-charts 的原生能力。** TradingView 的图表库支持缩放、拖拽、多周期切换、叠加指标线、标注——这些是用户最想要的功能，而库已经加载了但从未使用。

## Constraints

- Python 量化后端（pandas/numpy/akshare）不可替代，不考虑用 TypeScript 重写
- 现有 50+ 个 REST API 端点需要保持兼容或平滑迁移
- 单人开发，需要控制工程量在 4-5 周内
- 数据库 SQLite，不需要更换
- 部署环境是本地机器（`uv run main.py web`），不需要考虑云端部署

## Premises

1. **后端基本不动，只加 CORS 和 WebSocket。** Flask API 路由已用 Blueprint 组织，返回 JSON，核心业务逻辑不变。需要：统一 URL 前缀风格、移除 SocketIO 死代码并重新实现真正的 WebSocket 推送、添加 CORS 支持。

2. **前端从零搭建 React SPA。** 旧的 `index.html` 和新 React 应用是两套独立的东西，不存在渐进式迁移。React SPA 用 Vite 构建，开发时 proxy 到 Flask。

3. **WebSocket 真正实现。** 当前 SocketIO 只有 connect/disconnect，从未 emit 过进度事件。需要在数据更新、选股、回测等长任务中真正实现进度推送。前端用 `socket.io-client` 接收。

4. **技术栈：React + TanStack Router + TanStack Query + lightweight-charts。** 不用 Next.js，不用 Redux。TanStack Query 的缓存管理已足够。Vite 做构建工具。

## Approaches Considered

### Approach A: 最小可行——Flask 托管 React 构建产物
React SPA 构建后由 Flask 直接 serve，不分离部署。
- Effort: M (约 2-3 周)
- Risk: Low
- Pros: 部署最简单（一个进程），不需要 CORS，WebSocket 同端口
- Cons: 前端开发体验差（每次改代码要重新 build），前后端仍耦合

### Approach B: 标准分离——Vite 独立前端 + Flask 纯 API
前端独立 Vite 项目，开发时 proxy 到 Flask，构建后部署为独立静态资源。
- Effort: L (约 3-4 周)
- Risk: Med
- Pros: HMR 热更新，前后端职责清晰，Vite 生态成熟
- Cons: 开发时需两个进程，需 CORS 配置

### Approach C: TanStack Start 全栈——前端框架接管后端
用 TanStack Start 重写后端 API，Flask 逐步废弃。
- Effort: XL (约 6-8 周)
- Risk: High
- Pros: 最现代技术栈，前后端共享类型
- Cons: 需重写全部 Python 后端为 TypeScript，量化生态无等价替代

## Recommended Approach

**方案 B：标准分离。** 原因：

1. Python 量化后端不可替代（pandas/numpy/akshare），方案 C 排除
2. 方案 A 开发体验太差——改一个按钮都要重新 build，3-4 周的开发周期会很痛苦
3. 方案 B 是标准做法——Vite 开发时 proxy 到 Flask，build 后 Flask 直接 serve 静态产物
4. TanStack Router + Query + lightweight-charts 的组合在 Vite 下有最好的生态支持

## Design Decisions

### D1: URL 前缀统一

**决策：保持现状，不统一前缀。** 4 个 Blueprint 用 `url_prefix`（dashboard/backtest/khunter/risk），5 个 API 路由文件在装饰器中写死全路径，另有 1 个 `views.py` 仅做模板渲染。前端 API 客户端封装一层 base URL 即可，不需要为此前端改造动后端路由。记录当前不一致性供后续清理。

### D2: 选股过程数据

**决策：后端需要改动策略返回格式。** 当前 `select_stocks(self, df, stock_name='') -> list` 只返回信号列表（dict），不包含过程数据。涉及约 13 个具体策略实现（`strategy/` 目录下 20 个 .py 文件，去掉基类和工具文件后 13 个），改动范围中等。

改动方案：在 `BaseStrategy` 基类中添加 `_rule_results` 列表收集机制，策略执行时自动记录每条规则的命中情况。`rules` 字段中的 `name` 来自策略参数名，`threshold` 来自 `config/strategy_params.yaml`，`weight` 来自 `config/strategy_weights.json`。

API 响应示例：
```json
{
  "stock_code": "600519",
  "stock_name": "贵州茅台",
  "signal": "buy",
  "score": 78,
  "rules": [
    {"name": "MACD金叉", "hit": true, "value": 0.05, "threshold": 0.0, "weight": 0.3},
    {"name": "成交量放大", "hit": false, "value": 1.2, "threshold": 1.5, "weight": 0.2},
    {"name": "站上20日均线", "hit": true, "value": 1850.0, "threshold": 1820.0, "weight": 0.5}
  ],
  "indicators": {
    "macd": 0.05,
    "volume_ratio": 1.2,
    "ma20": 1820.0
  }
}
```

### D3: 回测可视化数据

**决策：现有 API 已包含所需数据。** `/api/trading/backtest/results/<id>/trades` 返回交易记录，包含买入/卖出日期和价格。需要在前端将这些数据映射到 K 线图的时间轴上标注。

### D4: 前端项目位置

**决策：`frontend/` 子目录。** 保持单仓库，`main.py web` 启动时自动 serve `frontend/dist/`。

### D5: WebSocket 协议

事件命名和 payload 格式：

| 事件名                 | 触发场景     | Payload                                                                                                              |
| ---------------------- | ------------ | -------------------------------------------------------------------------------------------------------------------- |
| `data_update_progress` | 数据更新     | `{current: 127, total: 3000, stock_code: "600519", stock_name: "贵州茅台", phase: "kline", success: 120, failed: 7}` |
| `selection_progress`   | 选股执行     | `{current: 50, total: 3000, stock_code: "600519", stock_name: "贵州茅台", phase: "evaluating"}`                      |
| `backtest_progress`    | 回测运行     | `{current_day: 125, total_days: 250, current_date: "2024-06-15", pnl: 0.05, trades_count: 12}`                       |
| `task_completed`       | 任意任务完成 | `{task: "data_update", success: true, message: "更新完成，成功 2993 只，失败 7 只"}`                                 |
| `task_error`           | 任意任务失败 | `{task: "backtest", error: "数据库连接超时"}`                                                                        |

### D6: URL 路由映射

React 路径 → 后端 API 端点：

| React 路径           | 页面     | 主要 API 端点                                        |
| -------------------- | -------- | ---------------------------------------------------- |
| `/`                  | 仪表盘   | `/api/stats`, `/api/dashboard/*`, `/api/risk/status` |
| `/stocks`            | 股票列表 | `/api/stocks`, `/api/stock/<code>`                   |
| `/selection`         | 选股     | `/api/select`, `/api/strategies/names`               |
| `/selection/history` | 选股历史 | `/api/selection-history`                             |
| `/analysis`          | 个股分析 | `/api/analyze-stock`, `/api/analysis-history`        |
| `/strategies`        | 策略管理 | `/api/strategies`, `/api/strategies/<name>/params`   |
| `/backtest`          | 回测     | `/api/trading/backtest/*`                            |
| `/khunter`           | 狩猎场   | `/api/khunter/*`                                     |
| `/risk`              | 风险监控 | `/api/risk/*`                                        |
| `/system`            | 系统管理 | `/api/config`, `/api/update`, `/api/data/*`          |

### D7: TypeScript 类型策略

**Zod schema + 自动推导 TypeScript 类型。** 在 `frontend/src/types/api/` 下定义 Zod schema，运行时校验 API 响应，编译时自动推导 TS 类型。这样类型定义和校验逻辑合一，不需要手写 interface。

### D8: 测试策略

- **前端组件测试**：Vitest + Testing Library，覆盖核心交互组件（K 线图、选股结果、回测配置）
- **后端 API 测试**：保持现有 `tests/` 目录的测试通过，新增 WebSocket 推送的测试
- **E2E 测试**：暂不引入 Playwright/Cypress，3-4 周周期内优先保证功能可用，后续迭代补充

## Success Criteria

1. 用户能在 K 线图上看到选股信号位置（命中点标注）
2. 用户能在 K 线图上看到回测买卖点
3. K 线图支持缩放、拖拽、切换周期（日/周/月）
4. 数据更新、选股、回测有实时进度推送（WebSocket）
5. 前端开发时 HMR 热更新，改代码即刻生效
6. 所有现有功能在 React 前端中可正常使用

## Distribution Plan

现有部署方式：`uv run main.py web` 启动 Flask 服务器。

迁移后：
- **开发环境**：两个终端——`uv run main.py web`（Flask API，端口 8080）+ `cd frontend && npm run dev`（Vite dev server，端口 5173，proxy 到 8080）
- **生产环境**：`npm run build` 构建 React 产物到 `frontend/dist/`，Flask 通过 `static_folder` serve 构建产物。需要一个 catch-all 路由，将非 `/api/*` 的请求 fallback 到 `index.html`（SPA 客户端路由标准做法）。不需要 nginx。
- **现有 `main.py web` 命令保持不变**，用户无需改变启动方式

## Next Steps

### Phase 1：项目搭建（1-2 天）
- 在 `frontend/` 目录创建 Vite + React + TypeScript 项目
- 安装 TanStack Router、TanStack Query、lightweight-charts、socket.io-client
- 配置 Vite proxy 到 Flask 8080 端口
- 搭建基础路由结构（对应 D6 路由映射表的 10 个页面）
- 定义 Zod schema 基础类型（D7）

### Phase 2：API 层 + WebSocket（5-6 天）
- 后端添加 CORS 支持（flask-cors）
- 后端移除 SocketIO 死代码，用 `flask-socketio` 重新实现真正的 WebSocket 推送
- 后端在 `data_collection_service`、`backtest_batch_queue`、`strategy_runner` 中接入 SocketIO emit（D5 协议）
- 后端扩展选股策略返回格式，包含过程数据（D2，涉及 `strategy/` 下 ~13 个策略文件）
- 前端封装 API 客户端（TanStack Query hooks + Zod 校验）
- 前端实现 WebSocket 连接管理，含断连重连策略：自动重连 3 次（间隔 1s/2s/4s），失败后降级为 TanStack Query 轮询（间隔 5 秒，轮询 `/api/update/status`、`/api/data/init/progress` 等现有状态接口），任务完成（`task_completed` 事件或状态返回 `running: false`）后停止轮询并尝试恢复 WebSocket 连接
- 前端全局 Toast 通知组件（WebSocket 断连/重连提示）

### Phase 3a：K 线图组件（3-5 天）
- lightweight-charts 集成，替换原生 Canvas 实现
- 支持缩放、拖拽、切换周期（日/周/月）
- 叠加 MA5/MA10/MA20 均线
- 成交量副图
- 信号标注 API——接收标注数据（买入/卖出/命中点），渲染在 K 线图上

### Phase 3b：仪表盘 + 选股页面（3-5 天）
- 仪表盘（dashboard）——统计数据、金股、热门板块、市场温度
- 选股（selection）——运行选股、结果展示、过程可视化（D2 规则命中/未命中表格）
- 选股信号在 K 线图上标注
- 选股历史查询

### Phase 4：高级功能迁移（1-1.5 周）
- 回测（backtest）——配置、运行、结果可视化、买卖点标注在 K 线图上（利用 K 线图组件的标注 API）
- 策略管理（strategies）——参数编辑、验证
- 狩猎场（khunter）——KHunter 筛选/追踪
- 数据管理（system）——数据更新、初始化、WebSocket 进度推送

### Phase 5：收尾（2-3 天）
- 风险监控（risk）
- 个股分析（analysis）
- 将旧前端移至 `web/templates_legacy/` 备份，确认无功能缺失后再删除
- 端到端测试（D8：Vitest 组件测试 + 后端 API 测试保持通过）

## Reviewer Concerns

经过 3 轮评审，以下问题在设计阶段无法完全解决，需要在实现时处理：

1. **WebSocket 降级轮询端点存在性**——`/api/update/status` 和 `/api/data/init/progress` 需要在实现时验证是否存在，不存在则需新增。
2. **WebSocket `phase` 字段枚举**——`data_update_progress` 的 phase 值（kline/basic/fund_flow 等）需从 `data_collection_service` 的现有阶段定义中提取，设计阶段无法穷举。
3. **SocketIO `async_mode="threading"` 限制**——单人本地部署场景下足够，但长时间回测任务中多客户端连接可能耗尽线程。如需扩展，后续可切换到 `eventlet` 模式。
4. **lightweight-charts React 集成方式**——优先使用 `useRef` + `useEffect` 手动封装（更灵活），如遇版本兼容问题再考虑 `lightweight-charts-react-wrapper`。
5. **Phase 2 工作量风险**——策略返回格式改动（D2）可能被低估，如超期可将 D2 改动提前到 Phase 1 或延后到 Phase 3b。
